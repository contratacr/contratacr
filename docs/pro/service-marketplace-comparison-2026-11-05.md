## Síntesis: no existe un menú idéntico en las veinte

Son tres modelos distintos: directorio/confianza (Yelp/Houzz), solicitudes y propuestas (Cronoshare/Zaask/GetNinjas/Bark) y contratación/reserva de servicios definidos (Webel/Urban Company/Fiverr). Algunas combinan modelos. Hogarú tiene una operación especializada, y Upwork/Workana/Freelancer sirven especialmente a trabajo remoto. Una descripción de producto no acredita que todo servicio tenga reserva, seguro, pago o verificación.

El patrón común útil es: **encontrar o describir una necesidad → conocer al profesional → contactar o comparar una propuesta → acordar → realizar → conservar historial/confianza**. Las interfaces concretas y mecanismos de cobro varían. No se afirma que las veinte tengan calendario, inventario, CRM o factura fiscal propia.

## Decisión para el alcance local de ContrataCR

La prioridad sigue siendo conectar personas y profesionales de Costa Rica y facilitar que el servicio ocurra. Replicar GTI completo sí desvía el propósito. Agenda, cotización sencilla, cambios de propuesta, historial y contactos reutilizados apoyan el propósito; impuestos especiales, CABYS, nómina, contabilidad o administración de bodega no deben dictar la navegación principal.

| Lo que ya tiene ContrataCR/Pro local | Decisión |
| --- | --- |
| Buscar profesionales por servicio/zona, perfil, fotos, verificación y reseñas | Núcleo existente. Mejorar claridad/calidad, no crear otra búsqueda |
| Proyectos con necesidad y propuestas | Núcleo existente. Reutilizar cliente, servicio y contexto; evitar una nueva sección Solicitudes paralela |
| Mensajes/WhatsApp | Contacto en el mismo contexto; no obligar a instalar la app para pedir un servicio |
| Cotizaciones con aceptar/pedir cambios e historial | Conservar simple; detalle avanzado solo al necesitarlo |
| Agenda/trabajos y reprogramación | Conservar como seguimiento del servicio, no como módulo administrativo independiente del cliente |
| Clientes | Conservar como apoyo profesional, sin pedir cédula/contactos para toda interacción ni revelar privados por identificación |
| Materiales/catálogo, costos, gastos y abonos | Opcionales, reutilizables dentro del trabajo; no exigirlos para terminar un servicio |
| Facturación avanzada/borradores | Preservar datos y acceso secundario actual. Congelar expansión fiscal; no borrar ni abrir otra rama |
| Empleos/promociones y funciones habituales | Preservar la navegación existente; no reemplazarla por un ERP |

Esto es una decisión de foco y prioridad, no una orden de borrar módulos. No se cambió nuevamente el menú sin evidencia de un problema concreto.

## Qué medir antes de seguir agregando

Priorizar abandono al solicitar, tiempo hasta primera respuesta, proporción de proyectos con cotización/aceptación, servicios terminados, satisfacción y repetición. Son criterios propuestos: no se inventan mediciones actuales. Mejorar campos obligatorios, contexto precargado, siguiente acción, mensajes vacíos y retorno. Las solicitudes de citas ya ofrecen «Pedir otra visita»; no construir una sección duplicada de recontratación. Revisar reseñas/contactos existentes antes de proponer reemplazos.

No copiar por inercia: pago por leads, custodia de dinero, seguros, IA autónoma, rastreo en tiempo real, nómina o veinte filtros. Cada función necesita demanda demostrable y mantenimiento proporcional. El número de secciones no es una métrica de valor.

## Avance técnico de esta ronda

Se fijó un candidato v1 del primer tramo de normalización mediante un manifiesto con orden y SHA-256, fuera de `supabase/migrations`. El ensayo ejecuta únicamente PostgreSQL en memoria, con documentos ficticios poblados y dispersos; valida equivalencia completa, revisiones/fechas, respaldos, filas normalizadas, rechazo de reaplicación accidental y aislamiento. No es la migración completa de todas las funciones añadidas ni un instalador para producción. Las API siguen sin habilitarse fuera de desarrollo.
