# Administrator MFA — 2026-10-19

## Policy and boundaries

Administrator role is read from `profiles` using the service client, never from editable user metadata. Every existing admin page/API using `getAdminUser`, `getApiAdmin` or `requireAdmin` now additionally requires:

- An enabled live administrator account.
- A currently verified TOTP factor on the live Supabase user.
- A cryptographically verified, unexpired JWT whose subject is that user.
- `aal2` and a successful `totp`/`mfa/totp` AMR timestamp less than 15 minutes old.

Token refresh, email OTP, Google/Apple or the password alone do not satisfy the second factor. Refreshing a token does not restart the TOTP window. Removing the factor revokes panel access even with a previous AAL2 token. MFA is required only to enter and operate the admin panel; ordinary account features and nonadministrator users are unchanged. `/admin` displays setup/challenge and nested protected pages redirect there. Every privileged API independently enforces freshness even if an already-open tab is suspended. The panel entry is never granted from editable user metadata.

Isaac approved the recommended timing and clarified that it applies only to administrators and the admin panel. No database migration or paid SMS provider is involved. Supabase TOTP is free and enabled by default, but environment enrollment is tested rather than assumed.

## Setup and recovery

The real account's owner must scan its QR in an authenticator and enter its code directly in the app. The agent must not enroll/retain the real account's TOTP secret. The QR/manual key stay in component memory; no storage, logs, analytics, email or support ticket receives them. Enrollment begins only on the explicit Configure button. Interrupted unverified factors bearing this setup's name may be replaced; verified factors are never deleted by the UI.

Before relying on a single device, retain the manual key privately in a password manager or use the authenticator's secured backup. If the authenticator is lost, recovery requires the Supabase project owner to verify ownership and reset the factor using Supabase's administrative MFA tools. There is no password/email-only bypass inside ContrataCR and no invented recovery-code system. Signing out remains available on setup and challenge.

## Regression

- `admin-mfa-guard.spec.ts`: missing session, nonadmin, disabled account, removed factor, AAL1, old TOTP, invalid JWT signature and subject mismatch denied; valid recent admin accepted.
- `admin-mfa.spec.ts`: RFC TOTP vector, timestamp boundaries and real TEST enrollment/challenge; privileged APIs denied before MFA, allowed afterward, denied again after new password login. Browser-native mode on mobile projects. No production factors modified.
- Existing disposable administrator tests complete real TOTP via `admin-mfa-helper.ts`; no production test bypass is added. Test secrets are worker-memory-only, limited to disposable `@contratacr.test` accounts on the isolated test project, and disappear with account cleanup. Do not screenshot a real enrollment QR.
- Signed-out admin, nonadmin/metadata spoofing, all read-only panel sections and font-independent branding remain in the focused browser run.

No App Store or Google Play submission is part of this change. Production activation and the real administrator's enrollment must be reported separately from implementation/testing.

## Validation and rollout

- Cloudflare/OpenNext production build, TypeScript, UTF-8, scoped lint and brand asset contracts passed.
- 36 focused cases passed in desktop Chromium, mobile Chromium and mobile WebKit: JWT/factor guards, real TOTP enrollment, a new password session and brand stability.
- 5 desktop admin smoke cases passed, including both nonadmin roles with forged editable admin metadata, signed-out APIs and every listed panel section. The stale identification-page test label was aligned with the existing “Consultar identificación” heading.
- Read-only production audit found two existing administrator accounts, neither with a verified TOTP factor. Their permissions were preserved; Isaac was informed and asked about the second account. No real account was enrolled or modified by these tests.
- The actual owner must complete the one-time setup after deployment; code deployment alone is not enrollment. No store release.

The focused MFA specs are included in push smoke and Safari CI. Local Supabase explicitly enables TOTP enrollment/verification. Test helpers reuse the existing production-denial target guard, allowing only the isolated regression project or explicitly configured local CI, with disposable email identities.
