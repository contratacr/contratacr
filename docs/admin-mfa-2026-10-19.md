# Administrator MFA — 2026-10-19

## Policy and boundaries

Administrator role is read from `profiles` using the service client, never from editable user metadata. Every existing admin page/API using `getAdminUser`, `getApiAdmin` or `requireAdmin` now additionally requires:

- An enabled live administrator account.
- A currently verified TOTP factor on the live Supabase user.
- A cryptographically verified, unexpired JWT whose subject is that user.
- `aal2` and a successful `totp`/`mfa/totp` AMR timestamp belonging to the verified session (no future timestamp).

Token refresh, email OTP, Google/Apple or the password alone do not satisfy the second factor. A completed second factor remains valid through token refresh in the same session; opening the panel again after 15 minutes does not restart the challenge. Removing an administrator's factor revokes panel access even with a previous AAL2 token.

The owner subsequently approved optional TOTP in Account/Security for all accounts and mandatory TOTP after login for administrators, replacing the initial admin-panel-only/15-minute policy. The full-screen challenge uses a continuous white background, no card or app navigation, safe-area padding and the visual viewport for the keyboard. The native bridge, first-run cleanup and viewport observer remain mounted while private account surfaces are gated.

Ordinary users can enable MFA and must enter a current authenticator code before disabling it; the admin UI never offers disabling. Migration 247 enforces the live factor/role policy through a PostgREST pre-request hook (including SECURITY DEFINER RPCs) and restrictive policies on existing RLS tables in public plus storage.objects/storage.buckets. Existing ownership rules remain in force; internal Storage migration tables are excluded. New private Realtime tables must retain the same restrictive MFA policy. Authenticator apps require no SMS provider.

The shared API boundary also enforces MFA before any service-role route handler, using the same indexed database policy for AAL1 sessions. There is no editable metadata/cookie opt-out. Anonymous public access remains unchanged. The migration must be applied and validated before deploying code that calls session_mfa_satisfied.

## Setup and recovery

The real account's owner must scan its QR in an authenticator and enter its code directly in the app. The agent must not enroll/retain the real account's TOTP secret. The QR/manual key stay in component memory; no storage, logs, analytics, email or support ticket receives them. Enrollment begins only on the explicit Configure button. Interrupted unverified factors bearing this setup's name may be replaced; verified factors are never deleted during setup. An ordinary account may explicitly disable its own factors after entering a current code.

Before relying on a single device, retain the manual key privately in a password manager or use the authenticator's secured backup. If the authenticator is lost, recovery requires the Supabase project owner to verify ownership and reset the factor using Supabase's administrative MFA tools. There is no password/email-only bypass inside ContrataCR and no invented recovery-code system. Signing out remains available on setup and challenge.

## Regression

- `admin-mfa-guard.spec.ts`: missing session, nonadmin, disabled account, removed factor, AAL1, future TOTP, invalid JWT signature and subject mismatch denied; valid administrator session accepted, including after 15 minutes.
- `admin-mfa.spec.ts`: RFC TOTP vector, timestamp boundaries and real TEST enrollment/challenge; privileged APIs denied before MFA, allowed afterward, denied again after new password login. Browser-native mode on mobile projects. No production factors modified.
- Existing disposable administrator tests complete real TOTP via `admin-mfa-helper.ts`; no production test bypass is added. Test secrets are worker-memory-only, limited to disposable `@contratacr.test` accounts on the isolated test project, and disappear with account cleanup. Do not screenshot a real enrollment QR.
- Signed-out admin, nonadmin/metadata spoofing, all read-only panel sections and font-independent branding remain in the focused browser run.

No App Store or Google Play submission is part of this change. Production activation and the real administrator's enrollment must be reported separately from implementation/testing.
